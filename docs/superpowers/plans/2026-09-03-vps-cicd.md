# VPS CI/CD Rollout Plan

**Status:** Implementation prepared on `main`; production rollout is gated and not enabled yet.

## Goal

Deploy `main` automatically to the Oracle ARM64 VPS only after CI/E2E passes, without rebuilding on the VPS and without replacing SQLite, uploads/music, backups, or `.env`.

## Architecture

- Normal quality/E2E jobs remain on GitHub-hosted x64 runners.
- Production release is rebuilt on `ubuntu-24.04-arm` because `better-sqlite3` is architecture-specific.
- Next.js uses `output: "standalone"` for the release artifact.
- VPS uses immutable `releases/<commit-sha>` plus `current` symlink.
- Persistent runtime state lives under `shared/.env`, `shared/data`, and `shared/uploads`.
- PM2 runs the standalone `server.js`.
- Deployment uses strict SSH host-key checking.
- New release must pass localhost HTTP health check or CD rolls back.
- Keep latest five releases.

## Rollout gate

Auto CD remains disabled until production access is configured.

Required production secrets:

- `VPS_HOST`
- `VPS_USER`
- `VPS_SSH_PRIVATE_KEY`
- `VPS_KNOWN_HOSTS`

Required/recommended variables:

- `VPS_APP_ROOT`
- `VPS_PORT` (default 22)
- `VPS_APP_PORT` (default 3000)
- `CD_ENABLED` (set to `true` only after the first manual deployment succeeds)

## First rollout

1. Pull current `main` on the VPS.
2. Run `bash deploy/bootstrap-shared-storage.sh "$(pwd)"` in the existing app root.
3. Verify `.env`, `data`, and `public/uploads` resolve into `shared/` and the legacy PM2 app still works.
4. Add production SSH secrets/variables in GitHub.
5. Run `Actions → CI → Run workflow` with `deploy_to_vps=true` while `CD_ENABLED` is still false.
6. Verify the production site, PM2, `DEPLOYED_REVISION`, SQLite data, uploads/music, and admin login.
7. Set `CD_ENABLED=true` to enable automatic deployment for future successful pushes to `main`.
